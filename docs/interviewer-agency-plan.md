# 面试官从"状态机的配音"变成"拿着材料的面试官"：架构方案（2026-09-14，已实施）

## 0. 这场（`cmu0imdid…`，抖音 Agent 研发 JD，interviewer-v10）发生了什么

| 回合 | 现象 | 机制 |
|---|---|---|
| 1 | 自我介绍说"一个多智能体和一个后端全栈项目"，面试官直接问 Study Assistant | 简报把 Study Assistant 定为主项目，`open_thread` 只能开简报里的题；候选人提到的"全栈项目"不在简报里，面试官没法接 |
| 1–11 | 主项目五个角度全走完，追问全在记忆 / 摘要 / 画像上；第二个项目没到 | 备课把 module 角度定在"分层记忆"（简历最亮的一行）；overview 的追问顺着候选人的记忆叙述走；hardest 的故障也是摘要。10 个回合是代码给项目阶段的预算，第二个项目排在五个角度之后 |
| 11–17 | 连问 6 道基础题，一道不追 | 基础阶段 6 回合是代码给的预算；提示词说"覆盖优先于深度"，模型就一题一问问满 6 道 |
| 15 | 候选人说"具体点"，面试官直接下一题 | "具体点"不在插话正则里，当成回答交给模型；基础阶段的规则是"只有关键词或答不上就 close_thread 换下一题，不追、不提示、不讲解"；模型没有"把问题说具体"这个动作 |
| 16 | 候选人答的是上一题（评测集），被记到 JSON 那题上 | 线程按回合切，不按内容 |

三条抱怨的共同点：**面试官能做的事是代码列好的六个动作，什么时候能做由代码判，模型只在"问哪句话"上有自由。** 只问一个项目、八股偏多、"具体点"被跳过，都是这个结构的直接产物。

## 1. 为什么当初这么设计

不是没道理，是每一步都有道理，加起来变成了现在这样：

1. **早期模型自由跑的时候出过的事**：面试官提前收尾、不追问、一次问三个问题、追问不贴候选人原话、换题时把 areaId 和问题配错、同一件事问两遍、候选人一句"不会"就给答案。每一件都加了一道代码门：预算、追问上限、复合问题拒绝、锚点校验、覆盖率门、thin 连击、连败退出、插话正则。
2. **评测与 trace 要确定性**：动作是枚举、状态是代码算的，评测才好写断言，trace 才好读。
3. **成本**：一回合两次调用（先决定、再说话）是为了让代码在模型开口前否决；对话原文按线程裁剪也是为了省 token。
4. **弱模型**：gpt-5.4-mini 级别的模型在长提示下会漏规则，所以规则越写越硬。

代价是：`interviewer/` 现在 3,658 行，8 月以来 24 次提交都在这个目录；每次用户反馈一个现象，修法都是"再加一条规则或改一句提示词"。用户这次点名了：这就是屎山的形成方式。

## 2. 结构诊断

现在的控制单位是**回合级动作门**：每回合模型提一个动作，代码用十几条规则判允不允许，不允许就换成代码的默认动作。模型没有：

- **计划权**：一场面试问几个项目、每个项目花多少、八股问几道，都是代码按节奏定死的数字（`PACE_PLAN`、`ANGLES_BY_RANK`），模型只能在数字里填空。
- **对话权**：追问、开题、关题、提示、收尾之外的动作不存在——澄清问题、把题说具体、换个问法、承接候选人提到的简报之外的东西、当场纠正、闲聊一句过渡，都做不了或只能硬塞进"说话"那一步。
- **判断权**：候选人一句话是回答还是插话由正则判；线程什么时候该关由 thinStreak 与上限判；该不该追由 lastAnswer + reason + 余量判。

上一轮的"宏观调控"是在这个结构里给模型看更多信息（剩余回合、余量、理由）。三场真机证明：信息给了，模型还是在代码划好的格子里做局部最优，第二个项目一次都没到。**格子本身是问题。**

## 3. 目标结构：模型拿计划，代码守底线

一句话：把"流程"从代码搬到模型的一份**面试计划（agenda）**里；代码只留三件事——总预算、切段落库、硬停。

### 3.1 一回合一次调用

面试官是一个 agent，一回合一次调用，边说边记账：

- 输入：材料（备课产出，见 3.3）、它自己写的计划、进度（用了几回合、还剩几回合）、工作记忆、近期对话原文。
- 输出：对候选人说的话（流式），加几次记账工具调用：
  - `plan`：写或改面试计划——要聊的项目、每个项目想碰的面、准备问几道基础题、场景题、大致各占多少回合。开场后写一次，之后想改随时改（"第一个项目讲得扎实，第二个项目留 4 回合"）。
  - `mark`：进入 / 离开一个话题（项目的某一面、一道基础题、场景题，或候选人自己提出来的东西），离开时给 verdict 与一句判断。切段、评分、报告都从这里来。
  - `note`：工作记忆（已确认、存疑、失守、简历假设的状态），不变。
  - `end`：收尾。

没有 open_thread / probe / close_thread / hint 这些动作了。追问、澄清、把题说具体、换个问法、提示、对质简历、承接候选人提到的项目，都是说话，模型自己决定。

### 3.2 代码守的底线（能数出来的全部）

| 底线 | 为什么留 |
|---|---|
| 总预算：节奏 = 一场几个回合（quick 12 / standard 20 / deep 32），到了强制收尾；安全上限 = 预算 × 1.5 + 4 | 用户定的宏观数字；没有它面试可能不结束 |
| 同一时刻一个进行中的话题；模型进入新话题没离开旧的，代码替它离开（verdict 空） | 切段需要边界；这是记账，不是控制 |
| 候选人点"结束"由代码执行 | 用户的操作必须生效 |
| 输入防御：JD / 简历 / 回答是不可信数据；对话原文按字符上限裁剪 | 不变 |

**删掉的**：阶段与阶段预算、角度集合的强制顺序、追问上限、thin 连击、连败退出、锚点校验、复合问题拒绝、开题覆盖率门、换题话语覆盖率门、过渡句规则、插话正则（除"结束"）、两步回合、`planTurn` / `ruleTurn` 的所有分支、`fallbackAction`。粗算 `budget.ts` 全删，`reducer.ts` 剩 1/4，`turn-agent.ts` 剩 1/3，`actions.ts` 剩记账工具，`prompt.ts` 重写。

### 3.3 备课改成"材料"，不是"题目清单"

备课产出不变形太多，但角色变了：从"代码按顺序开的题"变成"面试官手边的材料"：

- 项目：每个简历项目一份"档案"——弧线五个面各一条建议问法与要验证的线索、简历假设。不再分主项目 / 第二项目、不再规定第二个项目只碰两面；哪个项目多聊、聊几面，写在模型的计划里。
- 基础题池：抽样不变（角色配额、简历碰过加分），每道题带题目、追一层的方向、期望信号。问几道由计划定。
- 场景题：不变。
- 档位、评分表、假设硬门：不变。

### 3.4 体验与 trace

- 房间顶栏显示模型的计划与进度（"项目一 · 记忆层 → 工具链路 → 最难的问题 ｜ 项目二 ｜ 基础 4 道 ｜ 场景"，当前项高亮）。候选人第一次看得见面试官打算聊什么。
- trace 每回合记：计划（有改动时）、进入 / 离开的话题、verdict、模型开销。"为什么这么问"从模型的计划里读，不用再猜。
- 报告按计划里的话题分组。

### 3.5 体验版（网页版）

同构：View + 注入 + 纯函数复用（memory: trial-parity-architecture）。切段与状态是纯函数，两边一起换。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| 模型不写计划或不照计划走 | 计划每回合在提示词里、进度对着它显示；模型对自己写的承诺比对外部数字守得住（三场真机里"余量"信息它不理，但它会照自己的 plan 走——这是要验证的假设） |
| 模型又开始一次问三个问题、追问不贴原话 | 先当成提示词问题修；真的反复出现，再和用户讨论要不要加门。**不再默默加门** |
| 切段边界不准（模型忘了 mark） | 代码在模型进入新话题时自动离开旧的；整场没 mark 就整场一段——降级产出，不是报错 |
| 评测脚本与指标要重写 | 评测本来就只为简历上的数字跑一次（memory: regression-only-at-milestones），指标改成按 mark 算 |
| 弱模型漏规则 | 规则总数从二十多条降到几条，本身就是对弱模型的对策 |

## 5. 要用户定的

1. **走不走这条路**：这是重写 `interviewer/` 的一半，不是加功能。不走，就只剩调预算 / 减角度这种局部手段。
2. **按钮**：房间里"要个提示 / 跳过 / 结束"三个按钮，建议保留但改成给模型的消息（"我不太会，能给个方向吗" / "这题我想跳过"），只有"结束"仍由代码执行。
3. **节奏的含义**：改成一场的总回合数（12 / 20 / 32），不再分阶段。
4. **计划要不要给候选人看**：建议看（真实面试官不会亮计划，但这是练习工具，看得见自己被考什么面能减少"怎么又是记忆"的困惑）；不看也行，只进 trace。

## 8. 第二轮：问题的抓手、记账小修、成本（2026-09-14，已实施）

用户跑了一场（`cmu0pbcvv…`，多模态内容理解算法实习生，20 回合，总分 87）后说：整体不错，问题"宽泛"是指作为候选人不知道往哪个方向答；有些问题可以宽，有些要具体。另要控制 API 成本：减少无用上下文、提高缓存命中率。

### 8.1 问题的抓手（提示词与备课材料）

宽和窄各有形态：**开题可以宽，但要给一个抓手**（一个角度、一个例子、一个约束）；**追问必须窄**（一个机制、一个数字、一个决策）；一句只问一个要点，其余留到追问。这场里没抓手的："五层记忆分别怎么检索、怎么排序、冲突了怎么处理"，"业务方说提升留存你怎么拆"，"输入信号、正负样本怎么定义，再说建模和融合"。

1. 面试官原则第一条改成这条规则并给正反例；追问前先挑候选人话里最值得挖的一个点。
2. 备课的建议问法按同一规则写：背景架构与场景题的开题带抓手，其余角度和题池的题落到一个点；场景题的后续要点进引导阶梯，不塞进开题。`firstQuestion` 兜底照旧。

### 8.2 记账小修（代码，只改记账不加门）

3. 开场回合不接受 `enter`：自我介绍不成段（这场里自我介绍被当成项目题切段评分了）。
4. 同一句在一条话里原句重复两遍的折半（这场第 8 回合）。
5. 提示词：追问不换话题，不要 `leave` 再 `enter` 同一材料（这场场景题被拆成三段）；问题池里的题就是换话题，要 `enter`（这场第 6 回合把题池的题当项目追问，回答记错了段）。

### 8.3 成本

这场的实测：每一步的输入约 8.5k token（系统提示词 + 对话 + 工具定义），一回合 1–4 步——模型把 plan / enter / leave / note 一个一个调、每步都重发整段提示词，所以单回合输入在 8.5k（1 步）到 37k（4 步）之间，均值约 24k。缓存：没有记录 cacheReadTokens，无法知道命中率；但从提示词结构可以断定命中很差——进度、计划、当前话题、已结束话题、记忆这些每回合变的内容排在材料、JD、简历前面，前缀每回合都变。

6. **一回合一次记账调用**：把 plan / enter / leave / note / end 合成一个 `turn` 工具（各字段可空），模型一步记完账、下一步说话；`load_skill` 仍是独立工具。回合从 1–4 步降到最多 2 步（查技能包时 3 步）。
7. **系统提示词只放不变的**：人设、原则、工具说明、材料（不再标"已聊过"）、技能包索引、JD、简历。这些整场不变，是可缓存的前缀。
8. **变的东西放在最后一条用户消息里**：候选人这句话之后附一个"现场状态"块——进度、计划、当前话题（期望信号、待验证假设）、已结束话题、工作记忆、已聊过的材料 id。历史消息只留双方说的话，不带状态块。
9. **对话历史改成只追加**：不再按话题裁剪（现在换话题就丢旧线程，前缀跟着变），改为整场保留，超过上限（提高到 12k 字符，标准节奏一场用不满）才从最旧的整条丢。系统提示词 + 全部历史成为稳定前缀，每回合新增的只有最后一条用户消息；同一回合的第二步与第一步只差一次工具调用，几乎全命中。
10. **记录缓存**：`AgentRun` 记 `cacheReadTokens`（AI SDK 的 `usage.inputTokenDetails.cacheReadTokens`），trace 页每回合显示"tokens · 其中缓存 n"，改完能验证。
11. 不动：JD 与简历的截断长度（它们在缓存前缀里，只有首回合全价），评分与汇总调用。

估算：改后一回合约 2 步、每步输入约 9k，其中约 7–8k 走缓存价（OpenAI 缓存输入按一折计）；按全价折算约 3–4k/回合，比现在的均值 24k 低一个量级。这是估算，改完看 trace 里的实测。

### 8.4 顺序

先 6–10（结构改动，一起做一次真机看 token 与命中），再 1–5（提示词与记账），再真机一场看问法。

### 8.5 执行记录

代码（本地提交）：
- 成本：`turn` 单工具合并 plan / leave / enter / note / end（`actions.ts`）；提示词拆成整场不变的系统提示词（`buildInterviewerSystem`）与每回合的现场状态（`renderTurnMessage`，放最后一条用户消息里，"候选人说："之后才是候选人的话）；对话历史只追加、上限 12k 字符（`conversation.ts`）；`AgentRun.cachedTokens` 记 provider 报的缓存命中，trace 页显示。interviewer-v12。
- 问法：面试官原则第一段改成"开题给抓手、追问落一点、一句一个要点"带正反例；备课提示词同一规则（brief-v15）。
- 记账：开场回合不接受 enter；同一话题 leave 再 enter 视为继续；话开头的 JSON 去掉、原句重复两遍折半（`pickSpeech`）。

真机（抖音 Agent 研发 JD，标准节奏，脚本作答）：改后第一场 18 回合，输入 301,745 token，其中 237,568 命中缓存（79%），输出 9,262；每回合两步、输入 14–20k、缓存 6–18k、耗时 3–10 秒。按 OpenAI 缓存输入一折折算，每回合约 5k 全价 token，改前均值 24k。问法上看到了抓手："那分层记忆先别展开，挑你最熟的一层讲"，"那就只讲一层：常驻记忆是怎么写入的"；"具体点"被当场收窄。改后又修了两个记账毛病：JSON 后面跟着话的情况没被识别（第 5 回合把工具入参说给了候选人）；追问时 leave 再 enter 同一话题被拆成两段。

改后第二场 20 回合：输入 320,014 token，缓存 278,528（87%），每回合输入约 16k（两步）；没有 JSON 漏进话里；问题落到点上（"参数校验这一步，具体校验了哪些字段"，"5000 条里这个 8% 的基线是什么"）。又见一个记账毛病：面试官 leave 了却没 enter、接着在话题外追问了五回合，这五轮问答切不进任何一段——改成只 leave 不 enter 也不收尾的不认，话题继续。

## 9. 第三轮：答疑吃回合、场景题被挤掉、题池老是那几道（2026-09-14，已实施）

### 9.1 这场（`cmu1dgks5…`，标准 20 回合）发生了什么

计划记录（每回合的 `turn.plan` 入参）：

| 回合 | 计划 | 备注 |
|---|---|---|
| 1 | p1 6 + p2 4 + q1 2 + q4 2 + q2 1 + q5 1 + q6 1 + s1 3 = 20 | 开场那一回合已经花掉，实际只剩 19；计划第一天就超 1 |
| 10 | 项目聊完（9 回合），剩 10：q1 2 + q4 2 + q2 1 + q5 1 + q6 1 + s1 3 = 10 | 刚好；但计划写 1 回合的基础题每道都追了一层（q4、q2、q5、q6 各 2 回合） |
| 17 | 剩 3：q5 1 + q6 1 + s1 3 | 已经装不下，进了 q6 |
| 18 | 候选人问"DAU 是什么"，面试官答"日活，先看……"，计划 note："Q6 先把 DAU 解释清楚" | 答疑花了 1 回合 |
| 19 | 剩 1，提示词说"这是最后一回合：说完就 end"；面试官把场景题问出来并同时 `end` | 收尾语是一道题，候选人没机会答 |

三层原因，都不是"用户没按规则用"：

1. **预算的单位太粗**：一回合 = 面试官说一句，答疑（"DAU 是什么"）、复述（"再说一遍"）、换个说法（"具体点"）、给提示，跟一道新题的代价一样。真实面试按时间算，这些只值几秒。房间里的"要个提示 / 再说一遍"按钮也走这条路，所以按钮越好用、回合越少。
2. **算术没人做**：模型写了每项几回合，但没有人把它加起来跟剩余回合比；提示词到剩 3 回合才提醒"该收的收"，那时已经装不下了。计划写 1 回合的基础题每道都追了一层，也没被看见。
3. **末回合的指令有歧义**："说完就 end"被当成"问完就 end"。

### 9.2 方案（三条改动，一条要用户定）

**1. 答疑不算回合——模型标、代码认。** `turn` 工具加一个字段 `aside: boolean`："这句不推进面试：答疑、复述、换个说法、给方向，题还是原来那道"。代码把这句记成面试官侧的 `aside` 消息（现有 kind，今天只有候选人侧的"结束"用），`turnsUsed` 只数不是 aside 的面试官消息；话题的 `depth` 不加；切段时"追问 n"不含它（`segments` 已只取 probe），逐字稿保留；对话历史照给模型看；trace 标"答疑"。房间顶栏的"已说 / 总数"因此只数真的回合。

要用户定的底线：答疑要不要封顶。
- A. 不封顶：模型只在答疑时标，滥用能在 trace 里看见；候选人一直点"再说一遍"是他自己的事。
- B. **（建议）** 软顶：答疑超过 ⌈总回合 / 4⌉（标准节奏 5 句）之后按普通回合数。它是"一场总会结束"这条底线的一部分，正常用永远碰不到，不是流程门。

**2. 把算术摆到模型眼前（现场状态，不加门）。** 进度行后面加一行：计划里还没聊完的项合计约 N 回合（当前话题按"计划 − 已问"算），只剩 M；N > M 时写明"超 K 回合，改计划：砍基础题或压缩项目"。当前话题一行加"计划 x 回合，已问 y"。系统提示词的流程段补三句事实：开场那一回合也在总数里；场景题至少要两回合（一问、一收），排计划时给它留住；基础题一题一两回合、一场通常三四道，项目占大头。尾段的提醒改成：剩 ≤3 回合——还没问的场景题现在就得进，不要再开基础题；最后一回合——只告别，不提问、不 enter。

**3. 矛盾记账的底线（代码）。** 同一回合既 `enter` 新话题又 `end`：按进入算、丢掉 end——这句话是一道题，候选人得答；预算到头了下一回合代码用固定告别语收（现有）。这与"只 leave 不 enter 不认"是同一类：记账自相矛盾时取对候选人无害的那个解释。

### 9.3 题池为什么老是 RAG + 推理优化与部署

用这场的 JD 与简历跑 `topicWeight` / `sampleTopicPool`（ai-llm 12 个主题，池 10 道里领域包 6 道）：

| 主题 | 权重 | 200 次抽样入池 |
|---|---|---|
| Agent 架构与工具调用 | 2.36 | 77% |
| RAG 链路设计与失败归因 | 1.44 | 69% |
| 上下文工程与记忆 | 1.50 | 68% |
| MCP 与工具生态治理 | 1.43 | 63% |
| 提示工程与结构化输出 | 1.50 | 62% |
| 评估体系建设 | 0.90 | 53% |
| 成本与延迟治理 | 0.67 | 41% |
| 推理优化与部署 | 0.58 | 36% |
| 微调决策与方法 / 安全、注入与合规 | 0.50 | 28–29% |

四个原因：

1. **匹配按二字片段，权重被通用词决定**。`fragments("推理优化与部署")` = 推理 / 理优 / 优化 / 化与 / 与部 / 部署，"优化""设计""工程""链路"哪份 JD 和简历都有；"RAG 链路设计与失败归因"靠"设计""链路""失败"拿分，不是靠 RAG。JD 权重 ×2，所以通用词多的名字稳定在前。
2. **"简历碰过"全是真**：`topicFromResume` 是命中率 > 0——任何一个二字片段出现即算。40 个主题里 37 个标了"简历碰过"（这场题池 10 道全标）。+0.5 的简历加分是噪声，"从他项目里用到的东西出发问原理"这条备课指令也对所有题生效。
3. **模型问得多、按池的顺序问**：这场 5 道基础题（q1、q4、q2、q5、q6，几乎按材料顺序），9 个回合，池里 6 道领域题问了 5 道——池里有什么就问什么。前一轮用户已经说过八股偏多。
4. **最近问过的降权从来没生效**：`recentTopics` 只取岗位名完全相同的往期（`context.ts` 的 `sameJob`），这几场的岗位名分别是"Agent研发工程师 - 抖音""智能体与大模型应用工程""Agent开发工程师 - 豆包"，一次也没匹配上。

改法（4 与 5 是代码，6 是提示词）：

**4. 匹配改成整词。** 主题名按 与 / 、 / ：/ 括号 / 空格切成词（"推理优化与部署" → 推理优化、部署；"RAG 链路设计与失败归因" → rag、链路设计、失败归因），只有整词出现才算命中；`fromResume` 要求至少一半的词命中。单词名（"评估体系建设"）匹配不上就拿基础权重 0.5 靠随机进池——这正是要的多样性。测试里加"通用词不加分"的用例，改完用同一脚本对比 200 次抽样的分布。主题级关键词（SKILL.md 每个主题一行"关键词"）更准，但 33 个包 400 个主题是内容工程，这轮不做。

**5. 最近问过的按候选人算，不按岗位名。** 一个人最近几场问过的基础题降权，与他当时投的岗位名无关（`recentTopics` 改取最近 5 场全部，`recentWeaknesses` 仍按同岗位）。

**6. 基础题的分量写进流程段**（见 9.2 第 2 条："一场通常三四道，项目占大头"）；题池的说明加一句"按岗位重点挑，不按列表顺序"。

### 9.4 顺序与验证

先 1、3（记账）与 2（现场状态、提示词）一起，单测（reducer：aside 不计数、depth 不加、end + enter 取 enter；prompt：算术行）+ 真机一场（脚本作答，中间插一次"DAU 是什么"和一次"再说一遍"，看 aside 不计、场景题答上）。再 4、5、6，单测 + 同一份 JD 备课三次看题池。不动：预算收尾由模型说、题池语言包规则、材料瘦身（上一轮已搁置）。

### 9.5 执行记录

代码（本地提交，interviewer-v13）：
- 答疑：`turn.aside`；面试官侧 aside 消息不计回合、不加深度、切段的"追问 n"不含它；软顶 `asideAllowance = ⌈turns / 4⌉`，超过按普通回合数；标了 aside 却 enter 的按进入算。trace 标"答疑（不算回合）"。
- 矛盾记账：同一回合 enter + end 按进入算。
- 现场状态：进度行后加计划算术（没聊完的项合计约几回合、正在聊的按计划减已问、超几回合）；当前话题带"计划 x 回合，已问 y"；系统提示词流程段补开场计入、场景题留两回合、基础题三四道、答疑余量。
- 题池：`topicTerms` 整词匹配，`fromResume` 要求一半的词命中；最近问过的基础题按候选人算（本地版与体验版）；题池说明加"按岗位重点挑，不按列表顺序"。

题池分布（同一份抖音 Agent JD，200 次抽样入池频率）：改前 Agent 架构 77% / RAG 69% / 上下文 68% / MCP 63% / 提示工程 62% … 推理优化 36%，40 个主题 37 个标"简历碰过"；改后 Agent 架构 93%（JD 点名）、其余领域主题 40–65%（12 抽 6 的期望是 50%），"简历碰过"只剩真碰过的 3 个。

真机三场（脚本作答，中间插名词澄清、"再说一遍"、"要个提示"）：
1. 标准 20 回合：三处答疑都标了 aside、回合数不动，最后一回合只告别。但尾段提醒被无视——剩 3 回合时进了基础题、剩 2 回合还在追问，场景题没问上；模型在剩 3 回合时还整份重写了计划（新 id），✓ 全丢。输入 448k token，缓存 87%。
2. 快速 12 回合：提醒改成带场景题 id 与开题原句，仍被无视三次——模型顺着计划清单一项项往下走（q1 → q4 → q3），末回合还开了新话题，由预算固定收尾。
3. 提醒改成"计划清单上标 ← 这回合进 / ← 来不及了，不再问 + 现场状态最后一行"后：剩 3 回合时进了场景题，候选人答完，面试官自己收尾（提前一回合）。输入 217k，缓存 87%。

结论：这个模型看计划清单比看进度行认真，尾段控制要写到它读的地方；三场都没加代码门。另见到工作记忆的"存疑"条目大量重复（同一句写了五六遍），是记忆合并的事，这轮没动。
