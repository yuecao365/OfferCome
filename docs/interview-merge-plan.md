# 备课与面试合并成一个 agent loop（施工图）

> 状态：待放行。写于 2026-09-20。动代码前先过 §9 的闸门。

## 1. 为什么改：三个缺陷同一个病根

2026-09-19/20 的排查里查出三处缺陷，形态不同，根因相同——**都是交接产物**：

| 缺陷 | 实测 | 本质 |
|---|---|---|
| `InterviewArea.skill` 填充率低 | 163 道基础题里只有 53 道（32.5%）带包名 | 模型 A 要替模型 B 标数据，提示词还给了「拿不准填 null」的出口 |
| 分段丢能力项与难度 | 231 段里 79 段（34.2%）缺 `competencyId`、全部缺 `difficulty` | 评分要重新推断面试官本来就知道的事 |
| 技能包形同虚设 | 52 场里 `load_skill` 只调用 25 次 | 备课把包读完、写死成题目，面试官手上只剩执行，没有需要用包来决定的事 |

第三条最说明问题：**面试官不调包不是偷懒，是理性**。计划已经固定，包里的方法论在交接处蒸发了，只剩结论。

按「症状成组出现先找结构性原因」，该判的是结构，不是逐个打补丁。

## 2. 合什么、不合什么

分界线：**这段工作需不需要现场上下文与行动能力。**

**合并（备课 + 面试 → 一个 loop）**

备课的产出只有面试官消费。合并后，读包的 agent 就是问问题的 agent：计划是它自己第一步的工具调用，包的正文留在它自己的上下文里，整场都能用来判断「这一句追到位没有」。`skill` 字段随之消失——没有交接就没有标注需求。

**不合并（评分 / 示范 / 汇总 / 档案）**

这里是原则问题，不是流水线惯性：

> **评分的 agent 不能是面试的 agent。** 让模型给自己的表现打分，得到的是自我报告，不是测量。

整套评测（能力估计、与真值的秩相关、消融对照）成立的前提就是打分方独立。合并会直接摧毁它。何况这四个是事后批处理、可并行、不需要现场上下文。

**蓝图单独留着**：JD 级别、跨会话复用、可缓存，与具体某场无关。

## 3. 目标形状

```
job_blueprint（JD 级，缓存复用）
        ↓
┌──────────────────────────────────────────┐
│ 一个 loop：先规划，再面试                 │
│   工具：load_skill / write_plan            │
│         ask_candidate（挂起等候选人）      │
│         lookup_resume（仅简历超长时）      │
│   状态：事件日志，每回合从事件恢复         │
└──────────────────────────────────────────┘
        ↓ 事件日志
切段（纯代码）→ 评分 / 示范 / 汇总 / 档案（独立、可并行）
```

产品 agent 从 10 个降到约 6 个。**删掉的是交接本身，不是功能。**

## 4. 三处关键机制怎么映射

### 4.0 简历与上下文布局：什么进前缀，什么进历史

**简历从第 0 步就在稳定前缀里，不藏在工具后面。** 三个理由：

1. 第一步 `write_plan` 就要看全文——计划是从简历长出来的
2. 整场不变，天然属于缓存前缀
3. 可靠性：藏在工具后面 agent 可能不调，**这正是 `load_skill` 的失败模式，不该再犯一次**

唯一例外与今天一致：超过 `MAX_RESUME_CHARS`（6000）才节选，并给 `lookup_resume` 按关键词查原文。

产品层不变：用户在会话创建前挑或传简历，解析后冻结成 `resumeTextSnapshot`。

布局：

```
稳定前缀（整场不变，被提示词缓存吃掉）
  ├─ 人设 + 方法
  ├─ JD 节选 + 蓝图能力清单
  ├─ 简历全文（≤6000 字）
  ├─ 候选人档案摘录（跨场记忆，≤1200 字）
  ├─ 技能包索引
  └─ 议程 ← write_plan 之后补进来，之后固定
历史（只追加）
  ├─ load_skill → 包正文
  ├─ write_plan → 计划（同时落 briefJson）
  └─ ask_candidate ⇄ 候选人回答 …
```

**议程在规划完成后并进前缀**（不是留在历史里当工具结果），这样整场仍只有一个稳定前缀，与今天一致；代价是规划→面试的交界处掉一次缓存，只发生一次，可忽略。

### 4.1 候选人 = 挂起的工具

`runLoop` 已经有 confirm 档的挂起-恢复：工具没批准就记 `interrupted` 并返回 `{ status: "interrupted", pending }`，批准后带 `resume` 续跑。**候选人的回答就是这个「批准」。**

- 面试官调 `ask_candidate({ action, target, facet, why, ledger, reply })` → loop 挂起
- 候选人的话作为工具结果回来 → 下一回合从事件恢复 loop 续跑
- 35 分钟不需要长活进程：每回合是一次「从事件日志恢复 → 跑到下一次挂起」

### 4.2 动作校验 = 工具错误反馈

现在是「结构化输出 → 代码校验 → 违约把原因回传重出一次 → 仍违约代码定动作」，这段是 turn.ts 里的定制代码。

合并后：`ask_candidate` 的执行器做同样的合法性校验，非法就**返回一个错误的工具结果**（「switch 的 target 必须是材料 id，可选：p1、q1」），模型在同一个 loop 里看到错误自己改。这是工具调用的标准模式，不是定制流程。

底线不变：连续两次非法仍由代码定动作（loop 的 hook 里做），模型只负责说那句话。

**实测基线（合并后不得劣化）**：621 句发言中，95.0% 首次提议即合规、4.5% 重出后合规、0.5% 代码接管。

### 4.3 证据账 = 工具入参

`ledger` 现在是结构化输出的一个字段，合并后是 `ask_candidate` 的一个入参。数据不变，不多一次往返。

## 5. 阶段

### A. 候选人变成工具（不合并，只换执行形态）

- 新增 `ask_candidate` 工具与执行器（校验 + 落事件），`runTurn` 改为「恢复 loop → 跑到挂起」
- 动作校验从定制重出改为工具错误反馈；底线走 hook
- 简报仍由 brief-agent 单独产出，**本阶段不动备课**

**验收**：同一批冒烟场次，行为判定（`expectations`）不劣化；首次合规率、一句多问率、每回合输入 token 与缓存命中率对齐现有基线。

### B. 备课并进同一个 loop

- loop 开头几步：`lookup_resume` / `load_skill` / `write_plan`
- `write_plan` 的入参沿用 `briefOutputSchema`，执行器做同样的依据门禁校验，并照旧落 `briefJson`
- 删掉 brief-agent 的独立调用路径

**关键约束**：`briefJson` 的结构**一个字段都不改**（`skill` 除外，见 C 段）。下游 state.ts / progress.ts / cut.ts / views.ts / expectations.ts / postmortem.ts / 体验版路由 / 房间页全部不动。

**验收**：同一份 JD + 简历，产出的材料数、配额、依据分型分布与现在等价；下游零改动跑通。

### C. 删交接产物

- 删 `InterviewArea.skill`（schema、提示词那句「拿不准填 null」、兜底、状态卡里的 load 提示）
- 删 `packsForInterview` 与 `skillToLoad`——包已经在 loop 自己的上下文里，不需要再挑一遍、也不需要提示它去查
- 选包打平改**按分数 + 包名稳定排序**，不再靠目录加载顺序（现有 bug：test-qa 靠名字赢过 ai-llm）

**验收**：单测全绿 + 一场真机；`load_skill` 的调用不再依赖提示触发。

### D. 验证

- 合并前后各跑一轮：行为判定、能力估计与真值的秩相关 ρ、每回合输入 token、缓存命中率、每场成本
- `packs` 消融在合并后重跑一次：包留在 loop 上下文里之后，它到底有没有产出

## 6. 删除清单

| 删什么 | 为什么 |
|---|---|
| `InterviewArea.skill` 及其提示词、兜底、状态卡提示 | 模型填不准、代码能算准的字段 |
| `packsForInterview`、`skillToLoad` | 合并后没有「挑给面试官的包」这件事 |
| turn.ts 的重出流程（`call(retry)` / `call(forced)` 那套） | 由工具错误反馈 + hook 取代 |
| brief-agent 的独立调用路径 | 并入 loop |

## 7. 不做的

- **不合并评分 / 示范 / 汇总 / 档案**（独立性是评测的前提）
- **不动蓝图**（JD 级、可缓存）
- **不改 `briefJson` 结构**（除 `skill`），避免牵动整个下游
- 不趁机重排包的四段内容——那要等 §9 的消融结果

## 8. 风险

| 风险 | 说明 | 处置 |
|---|---|---|
| **上下文变长** | 今天的前缀**已经**含议程、简历、JD、档案摘录与包索引，所以真正新增的只有技能包**正文**（约 2k token）。现基线每回合输入 4.4k、缓存 77% → 预计约 6.4k（约 1.45 倍） | A 段就要量。超过 1.8 倍或缓存命中率跌破 70% 就回退 |
| 每回合调用数上升 | 一个回合可能两步（先 load_skill 再 ask） | 预算控住；量每场调用数与成本 |
| 单点失败面变大 | 一个 agent 同时要会规划和会追问 | 事件溯源恢复已有；失败落在单回合而不是整场 |
| 体验版同构 | `src/app/api/trial/*` 与本地版共用纯核心 | A、B 段都走同一份核心，路由层不动 |

**回退**：每阶段独立可回退；A 段保留旧 `runTurn` 路径一个提交周期，用开关切换对照。

## 9. 动工前的闸门

**先跑 `packs` 消融**（开关已在 `eval/switches.ts`，约 20 场、$2–3）。

- 关掉包与全开**没有差别** → 这套包机器本身没有产出。合并时应当**把它删掉而不是搬过去**：删 34 个包、选择器、渐进式披露、`skill` 字段，§5 的 B/C 段大幅缩小。
- **有差别** → 按本图施工，并在 D 段复测包在新结构下的贡献。

这个闸门比全套三档对照便宜一个量级，却决定了 B、C 两段的规模。
