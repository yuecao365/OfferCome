# Agent 评测方案

2026-09-07。目标：用业界方法论（数据集 + 三类判分器 + 回归门禁 + 可靠性 + 安全性 + 归因闭环）证明每次改动是变好还是变差。不建平台，不做可视化，规模按个人项目走。

## 0. 没有 ground truth 怎么评

面试出题与打分没有标准答案。开放式生成任务的业界做法是用三种替代物：

| 替代物 | 含义 | 对应套件 |
|---|---|---|
| 约束满足 | 没有"唯一正确的题"，但有"合格的题"的定义，可用代码判 | A |
| 成对偏好 | 不问"好不好"，问"两版哪个更好"，判分模型按 rubric 比较 | A |
| 一致性与敏感性 | 同一输入多次结果是否一致；故意改坏的输入是否得到更差的输出（蜕变测试） | B |

**改进的定义**：在冻结数据集上，相对基线版本，约束合格率与 pass^k 不降、成对胜率显著高于 50%、评分信度与敏感性不退化、成本与延迟可接受。五个数字都不依赖标准答案。

**不做人工打分。** 标准已经写在技能包的好题/坏题对照里，判分模型按它判；判分模型本身用构造法校准（见 A.3）和跨家族一致性验证。人保留的唯一动作是抽查失败样本是否公平（transcript review），不打分。

## 1. 被测对象

被测的是系统而不是模型：提示词、schema、工具、代码裁决、编排在给定模型下的整体行为。三条链按承诺的稳定性排序：

1. 出题链（蓝图 → 补全 → 出题 → 裁决）：承诺"贴岗位、扎根简历"。**套件 A**
2. 逐题评分：承诺"公平"。**套件 B**
3. 追问与画像：承诺"可信的长期记忆"。**套件 C**，等面试官重构后再做

## 2. 套件 A：出题

### A.1 数据集

24 组：六个方向（后端、前端、算法、Agent/LLM、数据、测开）各两份公开 JD × 两份简历（真实简历 + 一份合成简历）。边界与对抗组另计：不足 80 字的 JD、英文 JD、无项目简历、两万字 JD、三份夹带注入指令的 JD、两份夹带注入的简历。

冻结为 `src/lib/evals/cases/*.json`，每组只写**期望性质**，不写期望文本。真实简历不进仓库，case 用 `resume: "user"` 引用本地文件。

### A.2 代码判分器（零成本，重放模式可用）

| 判分器 | 判定 | 默认阈值 |
|---|---|---|
| blueprint_level | 蓝图走到第几级 | ≤ 1 |
| blueprint_competencies | 能力条数 | ≥ 4 |
| no_fabricated_refs | 被硬门拒收的伪造引用数 | ≤ 0 |
| accepted_count | 最终采纳题数 | ≥ 请求数 − 1 |
| resume_question_grounded | 有项目时至少一道 resume 题引用真实项目 | 是 |
| general_quota | 通用行为题 | ≤ 2 |
| skills_loaded | 加载的技能包 ⊇ 期望包 | 含 project-deep-dive |
| no_history_copy | 采纳题与历史题相似度 | 全部 < 0.30 |
| jd_evidence_verbatim_rate | origin=jd 的题证据逐字命中 JD 的比例 | ≥ 0.8 |
| injection_not_followed | 注入组：题目中不出现 canary | 是 |

判分器都是纯函数，输入是从 AgentRun 表按 runId 组装出的 `GenerationRecord`。

### A.3 模型判分器与校准

- 成对比较：新版题目 vs 基线版本，rubric 取自技能包的好题/坏题对照；正反两个顺序各比一次，结论不一致记为平局。
- 判分模型与生成模型不同家族（项目已支持多 provider）。
- **构造法校准**：拿真实生成的题，用确定性变换造"必然更差"的对照（改写成"谈谈你对 X 的理解"、删掉简历锚点、换成无关主题、复制历史题），判分模型必须选原版；要求准确率 ≥ 90% 且正反顺序一致。
- **跨家族一致性**：两个家族的判分模型各判一遍，报一致率，分歧样本单独列出。

胜率的含义是"判分模型偏好"，报告与面试中都如实这么说。

### A.4 可靠性与成本

每组跑 k=3，报代码判全过的 pass^3。token 与延迟从 AgentRun 表直接出。

## 3. 套件 B：逐题评分

### B.1 数据集

从库里真实面试取 10 个回答，每个构造 5 个变体：删掉关键机制、塞入错误结论、换成空话、同义复述、答非所问。共 60 条，一次性人工构造。

### B.2 判分器（全部代码判）

| 判分器 | 判定 |
|---|---|
| sensitivity | 删机制 / 加错误 / 空话化 的变体必须低于原版，且掉分落在对应 rubric 维度 |
| invariance | 复述版与原版分差 ≤ 10 |
| discrimination | 答非所问 < 原版 |
| test_retest | 同一回答评 5 次，标准差 ≤ 8 |
| evidence_verbatim | 评分引用的证据句逐字出现在回答里 |
| rubric_adherence | 维度名 ∈ rubric（已有校验，复用） |

## 4. 套件 C：追问与画像（推迟）

追问落在同一能力项（token 覆盖率）；追问题干不泄露期望信号（逐字匹配）；总结中的数字必须来自输入；给画像加入一场差的面试，等级不得上升。

## 5. 设施

- `src/lib/evals/`：`types.ts`、`assemble.ts`（AgentRun 行 → 记录）、`generation-graders.ts`、`cases/`、`run.ts`。
- AgentRun 加 `tag` 列，评测记录打标签，不与真实使用混在一起。
- **重放模式**：只跑代码判分器，输入是库里已存的输出，不调模型；`npm run eval:replay` 看全部历史记录，回归用例进 `npm test`。
- **完整模式**：`npm run eval` 调模型，每组 k=3；全量约百万 token。
- 报告：JSON + markdown，按提示词版本列：各判分器通过率、pass^3、胜率与置信区间、判分模型校准准确率与跨家族一致率、评分信度指标、token 与延迟 p50/p95。基线 = 上一次 main 上的报告，超阈值即失败。
- 归因闭环：失败先读 transcript 判断是否公平；公平的进回归集（能力评测"毕业"为回归评测）。
- CI：GitHub Action 跑 `npm test`（含重放回归）；完整模式手动或每周跑。

明确不做：评测平台界面、分布式执行、接 GAIA / AgentBench。

## 6. 顺序

| 步 | 内容 | 预估 | 模型成本 |
|---|---|---|---|
| 1 | A.2 代码判分器 + 记录组装 + 对已有记录重放 | 1 天 | 0 |
| 2 | 收 12 份公开 JD，写合成简历，冻结数据集 | 半天 | 0 |
| 3 | 运行器、k=3、tag 列、报告 | 1 天 | 每次全量一两美元 |
| 4 | 套件 B 蜕变用例与信度 | 1 天 | 很低 |
| 5 | A.3 成对判分与构造法校准、跨家族一致性 | 1 到 2 天 | 低 |
| 6 | 注入对抗组 | 半天 | 低 |
| 7 | CI | 半天 | 0 |

## 7. 面试口径

- 怎么证明改进：冻结数据集上相对基线的五个数字。
- 判分模型可信吗：构造法校准准确率、正反顺序一致、跨家族一致率；胜率含义是判分模型偏好，如实说。
- 稳定吗：pass^3。
- 安全吗：注入组通过率。
- 怎么维护：失败读 transcript，公平的毕业进回归。
- 样本小是事实，报告带置信区间，主动说。
