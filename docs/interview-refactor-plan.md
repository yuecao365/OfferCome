## 1. 要删的（不留平行实现）

- 面试中的记账结构：`interviewer/actions.ts`（turn 工具、plan / enter / leave / aside / end schema）、`interviewer/reducer.ts`（六条矛盾守卫）、`interviewer/memory.ts`（三列表与相似度合并）、`interviewer/progress.ts`、`state.ts` 里的 plan / threads / turnsUsed / aside 逻辑、`prompt.ts` 里的记账说明、计划算术、尾段提醒。
- 数据：`InterviewTurnDecision` 表、`MockInterviewSession.planJson / memoryJson`；`InterviewThread` 不再由面试中写入（改为整理员的投影，见 §2）。
- 前端：房间顶栏的计划条、trace 页的"进入 / 离开 / 改了计划"标记。
- 评测：`interviewer-metrics.ts` 里按记账数的指标（没交代就换题、代码接话次数）。
- 文档：`interviewer-agency-plan.md`、`interview-flow-during.md` 等 v8–v13 的流程文档标为历史；`interview-rebuild-plan.md` 删除（已并入设计文档）。

## 2. 数据模型（事件日志 + 投影）

新表 `InterviewEvent { id, sessionId, seq, type, payloadJson, runId?, createdAt }`，`@@unique([sessionId, seq])`。事件类型：`candidate_said / interviewer_said / notebook_written / tool_called / clock_tick / control / label_added / estimate_updated / critic_noted / segment_scored / fallback_used / model_error / ended`。

投影（为了不重写全部读路径，保留现有表作为物化视图，与事件在同一事务写）：
- `MockInterviewMessage`：由 `candidate_said / interviewer_said` 投影；房间与逐字稿照旧读它。
- `InterviewThread`：改由**整理员**产出（阶段 C），面试中不写；`planItemId / depth / verdict` 列删除，加 `startSeq / endSeq / competencyId / difficulty`。
- `MockInterviewSession`：删 `planJson / memoryJson`，加 `notebook`（最新一份）、`durationMinutes`、`clockJson`（最近一次时钟估计，纯展示）。
- `AgentRun` 已有输入 / 输出；事件带 `runId` 指向它，重放用。

重放：`replay(sessionId)` 读事件，用"录制模型"（从 AgentRun 取当时的输出）重跑编排器与后续流水线，不调模型。用于回归与调试。

## 3. 施工步骤

### 阶段 A：地基与基线（不改面试逻辑）

1. `InterviewEvent` 表 + 写入器；现有回合在落库时**同时**写事件（双写，一次迁移期）。
2. 重放器：`scripts/replay.ts <sessionId>`，读事件 + AgentRun 重跑切段与评分，不调模型。
3. 候选人模拟器 `scripts/simulate.ts`：
   - 合成候选人 = 简历 + 画像（扎实 / 一知半解 / 爱跑题 / 爱求助 / 对抗）+ **每项能力的真实水平**（从岗位能力模型采样，写进画像提示词："对 X 只懂术语不懂机制"）。
   - 用小模型按"只回答面试官刚才的问题"作答；走真实 HTTP 接口，是另一个客户端。
   - 复用 `lib/evals/fixtures.ts` 的 JD 夹具与简历。
4. 指标脚本：从事件日志算——聊了几个项目、每项目几面、基础题几道、场景题问没问、时长盒是否守住、重复提问（相似度）、求助后是否给方向而不是换题、每场 token / 缓存率 / p95；结果写 `evals/out/<run>.json` 与一张表。
5. **基线**：用现在的 v13 跑 5 画像 × 1 岗位 × 3 种子 = 15 场，留数字。这是简历上"改造前"的数。

验证：单测（事件写入、重放幂等）；15 场基线跑通。

### 阶段 B：面试官重建

1. 新 `interviewer/policy.ts`：一次调用，结构化输出 `{ say, notebook }`；工具只有 `lookup_skill`、`lookup_resume`。系统提示词 = 人设与方法（≤ 400 token）+ 材料 + 技能索引 + JD + 简历；历史只追加；现场卡 = 已用 / 总时长 + 上一回合笔记 +（阶段 C 起）聊过什么。
2. 时钟 `interviewer/clock.ts`：按双方字数与固定交换开销折算分钟，参数集中；90% 提醒、100% 收尾、交换次数 1.5 倍兜底。
3. 编排器 `interviewer/orchestrator.ts`：幂等、同一时刻一个回合、组装现场卡、调用、校验 `say`（长度、不泄露内部词）、写事件与投影（一个事务）、流式返回、降级（超时 → 固定话 + `fallback_used`）。
4. 删 §1 列的记账代码与表；`turn.ts / turn-agent.ts / session.ts` 按新形状收缩。
5. 房间：顶栏改为时钟（已用 / 总时长），去掉计划条；按钮照旧发候选人的话。trace 页：每回合显示笔记全文、开销、是否降级。
6. 体验版：会话文档 v8（events + notebook），`applyTurnPayload` 对齐。

验证：单测（时钟、编排器降级、输出校验）；模拟器 15 场对比基线（覆盖、重复、求助处理、成本）。

### 阶段 C：整理员与事后流水线接上

1. `aftermath/segmenter.ts`：面试结束后一次调用，从逐字稿切段（起止 seq、材料 id 或临场、种类、能力 id、难度层、一句判断），写 `InterviewThread` 投影与兼容的 `InterviewQuestion` 行 → 现有评分与报告照跑。幂等、可重跑。
2. 评分加引用逐字校验（引用不存在的结论丢弃并降置信）；同段双采样分歧大标低置信（先只记录，不改分）。
3. 面试中异步标注器（每 4 条消息一次，小模型）：产出 `label_added`，汇总成"聊过什么"回填现场卡；房间顶栏显示覆盖了哪些能力。
4. 指标脚本改用整理员的分段算追问深度与换题是否交代。

验证：重放旧会话得到同样的分段；模拟器 15 场看重复率下降与报告完整。

### 阶段 D：能力估计器

1. 材料补能力 id 与难度层（备课 schema 加字段，兜底按阶梯位置）。
2. 在线评委：小模型在每段结束（标注器判断话题切换）时打分与置信。
3. 估计器 `cognition/estimator.ts`：每项能力按难度分桶的 Beta 后验；输出"最值得追 / 已足够确定"一行进现场卡；停止规则进时钟提醒。
4. 模拟器的能力真值 ↔ 估计值：相关系数、达到置信的问答数。

### 阶段 E 及以后（各自独立放行）

评论员（开 / 关对比）→ 影子运行与灰度、仪表 → 语义记忆模块与检索 → 语音。

## 4. 每步的产出与提交

每阶段：计划已在此文档，放行后实施 → 单测 + 模拟器跑数 → 更新 `interview-flow-*.md`（重写为新流程）与本文档的执行记录 → 本地提交一次。

覆盖类指标（聊了几个项目、每项目几面、场景题问没问、项目段追问轮数）要等阶段 C 的整理员切段，这轮为 0，不是退步。

看到的事：
- **输出 token 降到三分之一、延迟降四成**：不再有工具入参 JSON，一回合一步。缓存命中率从 87% 降到 71%：回合少了、每场系统提示词的固定成本摊得少，且首回合全价；绝对输入仍少了 43%。
- **时钟折算偏紧**：标准 35 分钟只走了 13–18 回合（v13 是 19），候选人每分钟 120 字的折算把 250 字的回答算成 2 分钟。参数集中在 `CLOCK_RATES`，下一轮按真实作答速度校一次（或语音版直接用真实时间）。
- **一句多问**：205 句面试官提问里 107 句含两个以上问号（"我追两个点：第一…第二…"），违反"一句一个要点"。这是提示词与模型的事，不是流程的事，留到有整理员分段后一起用自博弈调。
- **泄露词过滤误伤**：adversarial-1 有一处注入后模型在拒绝时提到了"评分标准"，被换成了固定的话。过滤条件要改成"透露"而不是"提到"，留待下一轮。

## 8. 覆盖调整（2026-09-15，已放行并执行）

### 8.1 问题

阶段 C 的 15 场：基础题 0.6 道 / 场、场景题 33% 的场问到、项目段 104 / 122。v13 是 1.5 道 / 93%。面试官把时间几乎全花在项目上，用户体验上就是"一场下来只聊了项目"。

原因：
1. 面试官看不到"还没聊什么"。现场卡只有时钟、笔记、已聊过的材料名；没有按种类的账。标注器的标签已经能算出"基础题 0 道、场景题 0 道"，只是没给它看。
2. 提示词只说"项目占大头、再几道基础题、最后一道场景题"，没有时间分配的抓手；到 90% 才提醒收尾，那时已经来不及问场景题。v13 的经验：提醒写在进度行里模型不理，写在它正在看的清单上才管用。
3. 时钟折算偏紧：标准 35 分钟只走 13–18 回合，项目段刚聊开就到时间。

### 8.2 改法（提示词、现场卡、时钟参数；不加代码门）

1. **现场卡按种类记账**（`policy.renderTurnMessage`）：从标注器的标签算——"已聊：项目 2 面（背景架构、模块深挖）、基础题 0 道、场景题 0 道"；再给一行分配对照："这场默认分配：项目约六成、基础题约两成（三四道，一题一两句）、场景题约两成（留最后 5–7 分钟：一问一答再收）"，并按已用时间比例给出建议："项目已用 70% 的时间，该转基础题了" / "还剩 8 分钟，场景题还没问，这句就进"。这一行放在现场卡最后、紧贴"候选人说"（v13 学到的位置）。
2. **流程段补分配**（`policy.METHOD`）：把"真实一面的样子"那条改成带比例与顺序的写法，并写明"场景题必须问到，留够时间"；"一句只问一个要点"加一句"一个问号"（阶段 B 看到 205 句里 107 句两个以上问号）。

## 9. 阶段 D：能力估计器（2026-09-15，已执行）

设计 §6.1 的最简版本：把面试当自适应测验。岗位蓝图的能力（core / secondary）是被估计的量；每段问答是一次测量（难度 = 答到阶梯第几层，结果 = 在线评委的分数与置信）；估计器维护每项能力的后验，向面试官输出一行"最值得追 / 已足够确定"，面试官自己决定怎么问。

### 9.1 部件

1. **能力清单**：来自会话快照里的岗位蓝图（`contextSnapshotJson.jobBlueprint.competencies`，id / name / priority），`context.ts` 加 `competenciesOf()` 一处解析，编排器、后台、整理员、报告、模拟器共用。材料不加字段：quick / scenario 已有 competencyIds 作提示，项目面由评委按段判。
2. **在线分段**（`judge.ts` 纯函数 `closedSegments`）：从标注器的 label_added 推——act 为 open / switch 的那句开一段，下一句 open / switch / close 之前结束；已结束且还没评分（没有同 startSeq 的 segment_scored）的段交给评委。
3. **在线评委**（`judge.ts`，judge-v1，小模型一次调用）：输入这段逐字稿、碰到的材料（名称、线索、能力提示）、能力清单；输出 `{ competencyId, difficulty 1–4（答到阶梯第几层）, score 0–100, confidence 0–1, note }` → `segment_scored` 事件。跟在标注器后面、同一个 `after` 里顺序跑；写事件撞了 seq 就放弃，下次再评。
4. **估计器**（`estimator.ts` 纯函数）：每段折成能力证据 x = ((难度 − 1) + 分数/100) / 4 ∈ [0, 1]（低层答满 ≈ 0.25，最高层答满 ≈ 1）；每项能力 Beta(1, 1) 先验，按置信加权更新：均值 = (1 + Σ c·x) / (2 + Σ c)，置信 = n / (n + 2)，n = Σ c；权重 core 1 / secondary 0.6；下一个最值得追 = argmax 权重 × (1 − 置信)；"足够确定" = 置信 ≥ 0.6（约三段有效问答）。每次更新写 `estimate_updated`（trace 看），现场卡的一行从 `segment_scored` 现算。
5. **现场卡一行**（`policy.renderTurnMessage`，放在覆盖账之前）：`能力估计：最值得追：X（估计 中，置信 低，岗位权重 高）；已足够确定：Y（估计 高，置信 高）`；核心能力都足够确定时改为"核心能力都已足够确定：剩下的时间可以收尾"（停止规则）。流程段加一句：优先追最值得追的能力，措辞与角度自定；已足够确定的不必再问。
6. **事后**：整理员（segmenter-v4）每段也给 competencyId 与 difficulty，落 `InterviewThread.competencyId / difficulty`；报告页加"能力估计"一栏——用同一个估计器，输入换成事后分段 + 双采样评分（低置信的段置信 0.5）。
7. **指标**（模拟器能力真值已知）：在线估计与真值的相关（只算问到的能力）、事后估计与真值的相关、评过的段数、核心能力全部足够确定时用了几段（没到为 null）。`--recompute` 用 seed 重采真值。

- **sim-v2**：画像里每项能力带蓝图描述（`competenciesOf` 顺带取 description）；半懂 / 不会写成硬规则（不会：先说没做过、最多一两个名词、简历上写了也说是同事做的）；加"先判断这问考哪项能力，按那项的水平答""简历不能抬高水平""写完自查"。
- **judge-v2**：阶梯四层各一个锚定例子；要求逐字引用候选人原话作证据；代码修判断（`repairJudgement`，纯函数）：引用不在原话里降一层、把握打七折；引用里有"应该是 / 大概 / 记不清"最多第 2 层；分数夹进层的分数段（1：0–45，2：45–70，3：70–85，4：85–100）；能力 id 只认清单。
- `npm run rejudge -- <sessionId>`：用当前评委重评旧场次评过的段，只打印对照，不写库。
- 事后评分（evaluation-v3）没动：报告分数的口径不跟着在线评委走，等真实使用反馈。

验证（都用 `sim:estimator-1` 的 15 场）：
1. judge-v2 重评原来的 51 段（候选人仍是 sim-v1 的回答）：按画像的平均证据 solid 0.68 → 0.63、shaky 0.64 → 0.54、rambling 0.60 → 0.46、needy 0.68 → 0.60；v1 里五个画像挤在 0.60–0.68，v2 拉开到 0.46–0.63。
2. sim-v2 对 10 个弱项问题重答、judge-v2 打层：真值 0.8 的两段第 3 层 79–80 分；真值 0.5 的五段第 1–2 层 45–64 分（会说"记不太清""同事先定的"）；真值 0.2 的三段第 2 层 62–63 分（一段被归到别的能力后给了第 3 层）。0.8 与 0.5 分开了，0.2 与 0.5 还分不开——不会的候选人仍会把机制说个大概，下一版再把"不会"收紧。
3. 能力归属不稳：重评时约三成的段被归到另一项能力（c1 ↔ c9 / c4）。重评与探针都没给材料提示（materialId 为 null），真实运行里评委有材料的能力提示，会好一些；仍是下一轮要量的点。

4. **sim-v3 收紧"不会"**（同日，用户要求）：整段不许出现字段名 / 步骤 / 机制 / 数字 / 工具名，只能说"没做过 / 是同事做的 / 说不上来"，不超过 80 字；自查里出现了就整段重写。探针 8 个真值 0.2 的问题（16 次调用）：5 段答成"这个我不太了解……说不上来"，judge-v2 给第 1 层 20–30 分；3 段仍讲了机制（第 2 层 62–70 分）——都是候选人把那一问对到了另一项能力上（"连续调用同一工具怎么判断"、场景题），评委却记在 C1 下。平均证据 0.19（sim-v1 的回答在 judge-v2 下是 0.46–0.63）。三档现在分得开：0.8 ≈ 0.7、0.5 ≈ 0.4、0.2 ≈ 0.2。

结论：校准回路的机制通了，三档真值在探针上分得开；剩下的噪声是能力归属（候选人与评委对同一问各自对能力）。相关系数要重新跑才知道——按费用规则，等到下一次需要对照数字时再跑 15 场，不为这一步单独跑。

## 10. 阶段 E-1：评论员（2026-09-15，放行开工）

设计 §6.2：一个小模型每回合看最近几次交换，按"面试官该怎么做"的准则给至多一句提醒，注入下一回合的现场卡。异步、不阻塞、跑慢了就没有。它是过程监督的最小实现：盯行为准则，不盯结果。

### 10.1 部件

1. **评论员**（`critic.ts`，critic-v1）：跟在标注器、评委后面的第三个后台任务，每回合跑一次。输入最近 8 句逐字稿（面试官最后一句是被评的那句）、这场的时钟比例；准则五条（设计里的）：`stale_probe` 追问没贴着候选人上一句；`multi_ask` 一句多问；`help_ignored` 候选人求助 / 要求具体时没收窄反而换题；`rambling_unchecked` 候选人跑题没被指出；`over_probed` 同一点追了三轮以上。输出 `{ rule: 准则 id | null, note: 一句提醒 | null }`；没违反就 null，不写事件。违反 → `critic_noted { seq: 被评那句的编号, rule, text }`。
2. **现场卡一行**：只用**针对上一句**的提醒（`critic_noted.seq` = 逐字稿里面试官最后一句的编号），过时的不注入；放在能力估计一行之后、覆盖账之前：`评论员：上一句问了两个要点，这句只问一个。`。流程段加一句：评论员的提醒是对上一句的，照着改这一句，不复述。
3. **开 / 关**：会话字段 `flagsJson`（`{"critic": false}` 关；默认开），`flags.ts` 一处解析；模拟器 `--critic off` 创建会话后写这个字段。之后的影子 / 灰度也用这个字段，不再加列。
4. **指标**：`criticNotes`（提醒条数）、`criticNoteRate`（被提醒的回合 / 面试官回合）、按准则计数进 json；开 / 关对比看：违反率、求助后不换题、一句多问。
5. **trace 页**：每回合下显示评论员的提醒（准则 + 一句）。
6. 体验版没有后台，没有评论员（与标注器、评委一致）。

### 10.2 不做

评论员不改面试官的话（只提醒，不重写）；不给候选人看；不用评论员的输出改分数。

### 10.3 验证

单测（准则事件的取舍、现场卡只注入针对上一句的提醒、指标）；2 场冒烟（开）看提醒的命中与成本（每回合多一次小模型调用，约 1.5k 输入 token）。开 / 关 15 场对比按费用规则等下一次需要对照数字时再跑。

### 10.4 执行记录（2026-09-15，`sim:critic-smoke` 2 场，约 0.3 美元）

- 提醒 12 条 / 30 回合（37%）：multi_ask 9、help_ignored 3。逐条看：一句多问的判断基本准（被评的句子确实并列了两三个要点）；help_ignored 有一条判得勉强（面试官已经收窄到"你负责的那层"）。
- **提醒只注入了 5 / 12**：评论员排在标注器、评委之后，模拟候选人两秒就答，下一回合装状态时提醒还没写进去，就过时了 → 改成评论员最先跑（三步仍顺序，不并行，并行会争 seq）。真实用户打字慢，注入率会高得多；模拟器要量"开 / 关"时按注入后的回合看。
- 每回合多一次小模型调用（约 1.5k 输入 token、几十输出 token），每场输出 token 没有明显变化。

## 11. 阶段 E-2：影子运行与灰度、仪表（2026-09-15，已执行）

设计 §6.6：新版提示词 / 策略在真实对话上并行跑（不给用户看），输出交给评委与旧版比较；灰度按百分比放量；熔断后走固定话；每场一张仪表。可重放（`npm run replay`）阶段 A 已有。

### 11.1 部件

1. **策略变体**（`variants.ts`）：面试官策略以变体为单位——`{ id, label, promptVersion, extraRules }`，变体只在流程段末尾追加规则（系统提示词其余不变，缓存前缀不受影响）。先两个：`v2`（现状）与 `v2-terse`（问句不超过 60 字，先一句承接再一个问号，要点多的留到下一轮——针对评论员看到的"一句多问"）。变体 id 写进 AgentRun 的 promptVersion。
2. **灰度**：放量配置 `INTERVIEW_ROLLOUT`（环境变量，JSON：`{ live, canary: { variant, percent } | null, shadow }`，默认 `{ live: "v2", canary: null, shadow: null }`）。备课完成时按会话 id 的哈希分桶（同一场永远同一变体），写进 `flagsJson.policy`；已写了的（模拟器指定）不覆盖。回合装状态时按 `flagsJson.policy` 取变体。
3. **影子运行**：`flagsJson.shadow` 指定的变体在每回合落库后由后台再跑一次同样的现场卡（不流给房间、不改状态），写 `shadow_said { turnIndex, variant, say, notebook, rule }`，其中 rule 是评论员对影子那句的判断（与真身同一套准则）。比较全从事件算：影子 vs 真身的一句多问比例、被评论员提醒的比例、句长。开着的时候每回合多一次 actor 调用 + 一次评论员调用，所以默认关；模拟器 `--policy v2-terse --shadow v2-terse` 指定。
4. **熔断**：连续三回合模型没说出话（fallback）就不再调模型，用固定的话收尾，`ended.by = breaker`（额度 / 密钥 / 网络那类不可恢复的错误已经直接报给用户，不在此列）。预算超限切便宜模型不做：只配了一个模型。
5. **仪表**：trace 页顶部一块本场的数：变体与影子、输入 / 缓存 / 输出 token、缓存命中率、p95、兜底接话、评论员提醒；有影子时并排真身 vs 影子（一句多问、被提醒比例、平均句长）。数据从事件与 AgentRun 现算（`views.traceDashboard` 纯函数）。
6. **指标**：`variant`、`shadow: { turns, multiQuestionRate, criticRate }`，汇总表加影子的两行；模拟器结果 json 带变体。

### 11.2 不做

多模型的预算切换；影子输出给评委打分（评论员的准则判断够比较过程；结果分数留给自博弈的 A/B）；房间里显示灰度状态。

### 11.3 验证

单测（分桶确定且按百分比、放量配置解析、熔断、影子事件的投影与仪表）；1 场冒烟（`--policy v2 --shadow v2-terse`）看影子事件、仪表与成本。灰度与 A/B 的 15 场对照等需要对照数字时再跑。

### 11.4 执行记录（2026-09-15，`sim:shadow-smoke2` 1 场，真身 v2 + 影子 v2-terse，约 0.3 美元）

- 第一次冒烟影子没跑：备课完成时用入口处的会话快照填开关，把模拟器在备课期间写的 `shadow` 盖掉了 → 改成在事务里重读 `flagsJson` 再补。
- 第二次：14 回合，影子 13 句（收尾那句不跑影子）。真身 vs 影子：平均 70 字 vs 40 字；一句多问 8% vs 0%；被评论员判违反 36% vs 23%（影子的违反主要是 stale_probe——短问句更容易接不上候选人上一句）。仪表与逐回合的影子在 trace 页可见。
- 成本：每场输入 token 175k → 212k（+21%，影子那次 actor 调用大部分走缓存），输出 +9%。

结论：影子与灰度的机制通了；v2-terse 在"一句多问"上明显好、在"贴着上一句追问"上略差，是否放量要看 15 场 A/B（按费用规则等需要对照数字时再跑；到时 `INTERVIEW_ROLLOUT='{"canary":{"variant":"v2-terse","percent":50}}'` 或模拟器 `--policy v2-terse` 各跑一半）。

## 12. 阶段 E-3：语义记忆（2026-09-15，已执行）

设计 §8 第三层、§14"记忆机制"：候选人的说法 ↔ 证据 ↔ 能力，跨场；写入来自评委与整理员的产物，带置信与时间衰减；备课时带上上次弱项与问过的题，面试中可查"这条说法上次验过没"，估计器有跨场先验，冲突（上次说 X 这次说 Y）浮给面试官。

### 12.1 部件

1. **不加表**：记忆是对已有产物的读时物化——每场的 `hypothesesJson`（说法 + 验证结果）、线程的能力与层次 + 双采样评分（事后能力估计）、评分里的短板（point + 引用）、线程的第一问（问过什么）。同一份简历、已完成、非评测的场次，最近 10 场，按 `completedAt` 衰减（半衰期 30 天）。`memory-recall.ts` 一处读，产物是 `InterviewMemory`；备课完成时 recall 一次存进 `contextSnapshotJson.memory`（这场看到的记忆是快照，可重放）。
2. **说法的历史**（`memory.ts` 纯函数 `claimHistory`）：这场简报里的每条假设按简历原句相似度对上上几场的说法：上次已验证 / 上次没讲清 / 上次说法不同（前后场结论相反）。写进系统提示词"上几场的记忆"一段，项目材料里那条说法后面带上标注；面试官提示词加一句：上次没讲清的优先再验，说法不同的当面问。
3. **跨场先验**（`priorsFrom` + `estimate(…, priors)`）：上几场的事后能力估计折成 Beta 伪计数（样本数 × 衰减，每场每项最多 3），这场的估计器从它起步——现场卡的"最值得追"一开场就有方向，"已足够确定"可以更早出现。
4. **面试中可查**：只读工具 `lookup_memory(query)`，按相似度在说法、短板、问过的题里找（字符 n-gram，材料小不上向量）。
5. **备课**：现有的"最近失守的考点 / 最近问过什么"（`recent-feedback.ts`）就是记忆的两类条目，不重做；`memory-recall.ts` 复用它取短板与问过的题（同一简历的场次）。
6. **量**：`npm run recall -- <resumeId>` 打印一份简历的记忆、先验与最近一场简报的说法历史（零模型调用，用已有场次验证）。跨场先验让"核心能力定下来用了几段"少多少、上次弱项被再验的比例——需要同一简历连跑两场，等需要对照数字时用专门的夹具简历跑。

### 12.2 不做

向量检索与重排（材料小）；把画像模块（`candidate-profile/`，六维洞察）并进来——它是给用户看的画像，记忆是给面试官用的证据；两者读同一批评分。

### 12.3 验证

单测（衰减与先验、说法匹配与冲突、检索、提示词段）；对库里真实使用的简历跑 `recall`，人工看说法历史与先验合不合理；1 场冒烟看系统提示词里的记忆段与 lookup_memory（约 0.15 美元，只在有真实历史的简历上才有意义，冒烟用 recall 脚本代替）。

### 12.4 执行记录（2026-09-15，零模型调用）

- 真实使用的简历（10 场，都是重建前的旧格式）：说法 0、能力估计 0、短板 101、问过 73 题——旧场次没有假设验证与能力标注，记忆只有短板与问过的题；系统提示词段把短板按话题去重后取四条（不然一个话题的三条会挤掉别的）。
- 评测夹具简历（`--include-eval`，最近 10 场新格式）：说法 22 条、能力估计 36 条；最近一场简报的 5 条说法都对上了历史（2 条"上次说法不同"、2 条已验证、1 条没讲清，note 带整理员的原句）；跨场先验把 7 项能力的起点定在 0.5 左右、置信 0.3–0.9——起点都在 0.5 是那批场次评委 v1 偏松、估计挤在 0.5 的老问题，先验的机制本身对。
- 单测 437 通过；题池抽样的一个测试偶发失败（与本阶段无关，单跑三次都过，另开任务修）。

## 13. 阶段 E-4：语音（2026-09-15，已执行）

设计 §9"语音"：时钟换真实时间；actor 输出接 TTS 并支持先说前半句；候选人输入接 ASR；打断作为 control 事件。本期设计写的是"接口预留"，但重建后语音模式实际断了：录音组件（`mock-interview-voice-controls.tsx`）没有任何页面在用，转写接口还要旧流程的 questionId（面试中已经没有题目行）。所以 E-4 先把语音模式接回新房间，再做真实时间与流式朗读。

### 13.1 部件

1. **转写接口**（`/api/interviews/mock/[id]/transcribe`）：只认会话（进行中），收录音，返回 `{ transcript, voiceMetricsJson }`；语音指标不再往题目行上合并——随候选人那条消息以 `voiceMetricsJson` 交给 `/turn`（turn 接口已经收这个字段，存在消息的 metricsJson.voice 里，画像的口语流畅维度照旧从这里推导）。
2. **房间**：会话是语音模式时，作答区多一块录音控件（录 → 转写 → 直接作为这回合的回答发出，附语音指标）；文字框保留作兜底。面试官的话边流边读：按句号 / 问号 / 感叹号切句，流到一句就朗读一句（浏览器 speechSynthesis，中文取 zh 声音），流结束读完剩下的——"先说前半句"。开始录音就停止朗读（打断的最小实现；不写 control 事件，面试官不需要知道）。
3. **时钟**：语音模式用真实时间——已用分钟 = 现在 − 开场时刻（会话 `startedAt`），阶段与硬顶不变；文字模式仍按字数折算。`clock.ts` 的接口不变，多一个 `realTimeClock`；回合与房间视图按会话模式选。房间顶栏语音模式下按墙上时间每 15 秒走一次。
4. 体验版没有语音（没有转写模型的 BYO 配置），不动。

### 13.2 不做

服务端 TTS（浏览器自带够用）、VAD 自动断句、打断写成 control 事件（面试官不需要知道）、实时流式 ASR（一段录完再转写）。

### 13.3 验证

单测（真实时间的时钟：阶段、硬顶、开场前）；类型与 lint；浏览器打开一场语音模式的房间看录音控件与朗读（麦克风权限在自动化里拿不到，录音 → 转写这一步用接口单测 / 人工）；文字模式回归不受影响。

### 13.4 执行记录（2026-09-15，零模型调用）

- 转写接口只认会话、返回文字与语音指标；旧的按题目行合并语音指标的逻辑（`mergeVoiceMetrics`）连同测试删掉。
- 房间：语音模式下作答区多录音控件（"按下开始回答 / 说完了，发送"），转写完直接作为回合回答发出并带 `voiceMetricsJson`；面试官的话按句流式朗读，开始录音即停；文字框保留。
- 时钟：`realTimeClock`（真实时间）与折算版共用阶段与硬顶；语音会话的回合、房间视图都走它；顶栏每 15 秒按墙上时间刷新。单测 436 通过，类型与 lint 干净；设置页的"语音面试"选项与首页都能正常加载（无控制台错误）。录音 → 转写这一步自动化里拿不到麦克风，留人工核。
