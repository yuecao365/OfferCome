# 面试开始前：改进计划（v3 备课）

> 基于 [interview-flow-before.md](interview-flow-before.md) 描述的现状。目标只有一个：备课不再把 JD 当真相，同时保持产物可复现。
> 面试中、面试后另起计划，本篇不动它们；但本篇定下的数据结构要给后两阶段留好位置。

## 0. 三条原则

1. **JD 是弱信号**：素材优先级 简历 > 岗位基线（技能包）> JD。JD 过时或缺失时，由基线和简历补位，而不是暂停问用户或联网。
2. **可复现**：所有"岗位通常需要什么"的知识来自仓库内版本化的技能包，不来自联网。同一份 JD + 简历 + 节奏，领域集合应基本稳定。
3. **只改备课，不改自主性**：本篇新增的都是给面试官更好的"备课材料"和更清楚的标签；面试中怎么用由模型决定（面试中阶段再做）。

## 1. 三源合成：岗位基线（baseline）

### 现状
领域只来自蓝图，蓝图只看 JD。技能包只在备课时截 2500 字节选塞给模型，没有结构化地参与"这个岗位该考什么"。

### 改动
- 新增**岗位基线**：`recommendSkillPacks` 选出的包（简历权重 3、岗位名 2、JD 1，已有）→ 从每个包的"主题"抽出基线能力 `{ id: "B-<pack>-<n>", name, description, packName }`，origin=baseline。**纯代码，不调模型。**
- 简报 agent 的输入从"蓝图"变成"蓝图（origin=jd / inferred）+ 基线（origin=baseline）+ 简历与项目 + 已知弱项"。
- 提示词加权重规则（原文草案）：
  > 三份来源的可信度：候选人简历上可验证的经历最高；岗位基线（这个岗位通常考察什么）其次；JD 最低——JD 常常过时或只写了一部分。JD 与基线冲突时以基线为准，但 JD 独有且具体的要求要保留。领域的 competencyIds 可以引用蓝图能力（C-）或基线能力（B-）。
- 溯源：报告页"这道题在考察什么"对 B- 来源显示"岗位常见要求（来自技能包 X）"，对 inferred 显示现在的"非你提供的岗位描述"。

### 连带简化
- JD 充分性判断只保留一种暂停：JD 少于 80 字符且岗位名也匹配不到任何领域包。其余情况一律继续，因为基线兜底。
- 联网补全 agent 降为最后手段（仅上述极薄情形、用户主动选"AI 补全"时），默认路径不再联网。
- `requiredCompetenciesForPace` 改为"蓝图 + 基线"的合计数，几乎不会再触发复核。

## 2. 领域的风格与阶梯的风格

### 现状
kind 只有 technical / project / behavioral；technical 被要求从场景切入，纯知识题不会出现；阶梯是四句自由文本。

### 改动
- 领域加 `style`：technical 领域取 `scenario`（场景切入，现状）或 `fundamentals`（课纲式知识点，来自基线主题）；project / behavioral 不用填。评分表按 kind + style：

  | kind / style | 维度（权重） |
  |---|---|
  | technical · scenario | 技术正确性 50 · 分析与取舍 30 · 表达结构 20（现状） |
  | technical · fundamentals | 准确性 60 · 原理深度 25 · 表达结构 15（新增） |
  | project / behavioral | 不变 |

- 阶梯每级带风格标签：`ladder: [{ text, style: fact | principle | scenario | tradeoff }]`。备课时由模型标；面试中阶段再让 probe 工具回填实际风格。项目线程的阶梯于是可以写成"职责(fact) → 用到的原理(principle) → 故障场景(scenario) → 取舍(tradeoff)"，这就是"把八股和场景题融进项目线程"的**材料**，怎么问仍由面试官自己决定。
- 提示词只说明两种风格何时值得用，不规定数量：
  > fundamentals 领域适合岗位基线里的高频主题、且候选人简历没有直接项目可挂的知识点；scenario 领域适合 JD 或简历里有具体系统可以拿来设场景的方向。

## 3. 技能包深化（做深不做宽）

### 现状
10 个包、三层；正文是自由 markdown；备课按正则截"追问 / 阶梯 / 好题"段落。

### 改动
- 正文加一个结构化段 `## 主题`，每个主题固定四项：

  ```
  ### <主题名>
  阶梯: 入门 → 原理 → 场景 → 取舍（各一句）
  好题: 1–2 道
  危险信号: 常见的错误答案 / 只会背名词的表现
  期望信号: 好回答会出现的要点
  ```
- loader 解析主题为结构化对象；基线能力就从主题来（第 1 节）；备课注入改成按主题而不是按字符截。
- 先改三个包做样板：ai-llm、backend、cs-fundamentals。其余包保持自由正文，loader 对没有"主题"段的包退化为现状。
- 为面试中阶段预留：主题对象将来直接作为 `lookup_skill(topic)` 工具的返回，这是计划 4 里 RAG 的检索对象。本篇不做工具。

## 4. 简历假设：不动规则

evidence 必须逐字来自简历的硬门保留。它只约束"关于简历的断言"，不决定领域来源，第 1 节已经把来源问题解决。

## 5. 数据与兼容

- 简报加 `version: 3`；`parseStoredBrief` 对 v2 简报（无 style、阶梯为字符串数组）做只读兼容：style 视为 scenario，阶梯字符串包成 `{text, style: null}`。
- `InterviewQuestionEvaluation.generationMetadataJson` 加 `style` 与 `competencyOrigin`，报告页溯源用。
- 提示词版本升 interviewer-v3（简报提示词变了；回合提示词本篇不动，但版本号跟随简报）。

## 6. 评测钩子（无人评，全部可自动算）

备课改完就能跑的指标，用现有 43 份冻结 JD × 用户简历 / 合成简历：

| 指标 | 说明 | 期望 |
|---|---|---|
| 蓝图降级率 | level 2 / 3 的比例 | 不因本篇变化 |
| 基线参与率 | 领域 competencyIds 中含 B- 的比例 | 过时 / 极薄 JD 组显著高于完整 JD 组 |
| 假设证据通过率 | 模型给出的假设中通过逐字硬门的比例 | ≥ 0.8（现状约此水平） |
| 预算利用率 | plannedTurns / turnRange.max | 0.8–1.0 |
| 领域一致性 | 同一输入重复 3 次，领域名的三元组相似度 | 明显高于随机；不要求完全一致 |
| 风格分布 | fundamentals / scenario 领域数 | 技术岗两种都出现过 |
| 对抗组 | 注入指令 / 英文 JD / 极薄 JD | 不崩、注入标记不出现在简报里 |

## 7. 实施顺序与验收

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 技能包主题段 + loader 解析（三个样板包） | 单测：解析出主题；无主题段的包退化正常 |
| 2 | 岗位基线 + 简报三源输入 + 提示词权重规则 + 溯源 | 极薄 JD 一场：不暂停、领域含 B- 来源、报告溯源正确 |
| 3 | style + 阶梯风格标签 + 评分表 + v2 兼容 | 旧会话报告页照常；新简报含 style；全部测试通过 |
| 4 | 充分性简化、联网补全降为最后手段 | 80 字符以下 JD 仍能暂停询问；以上不再联网 |
| 5 | 评测脚本按第 6 节跑一遍，记录基线数字 | 数字进 docs/eval-plan.md |

预估 2 到 3 天。每步独立提交。

## 8. 待你定的三件事

1. 岗位基线是否允许模型参与（例如让模型从主题里挑）。我建议不参与，纯代码选，保证可复现。
2. fundamentals 评分表的权重数字。
3. JD 复核暂停是否保留（仅极薄情形）。我建议保留，去掉后极薄 JD 会全靠岗位名猜。
