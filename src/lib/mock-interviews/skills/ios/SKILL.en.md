## What interviewers care about

The day-to-day of an iOS engineer is writing business features in Swift (with a lot of Objective-C still in older projects) and Apple's framework stack: UIKit or SwiftUI screens, ViewModels and state flow, async/await or Combine for asynchrony, Core Data/SQLite/files for storage, Xcode projects and dependency management (SPM/CocoaPods), and App Store review and TestFlight staged rollout. In real interviews the dividing line for iOS questions is memory and the runtime: many can recite that ARC is reference counting, few can explain why a particular closure leaks, when weak and unowned will crash, or how Swift's copy-on-write for value types affects performance; many can say SwiftUI is declarative, few can explain where @State and @StateObject are stored differently and why a view gets rebuilt unexpectedly. Interviewers care about three things. First, real understanding of memory and the runtime (ARC, retain cycles, autoreleasepool, method dispatch, Runtime message forwarding). Second, the right mental model of concurrency (GCD queue semantics, Swift Concurrency actor isolation and structured cancellation, main-thread constraints). Third, a closed loop for production troubleshooting (how to use Instruments and attribute causes for jank, crashes, OOM, launch time, and app size).

Campus hiring leans toward Swift language features, ARC and retain cycles, UIKit basics (view hierarchy, AutoLayout, UITableView reuse), basic GCD usage, and basic Runtime concepts. Experienced hiring leans toward SwiftUI in production and mixed stacks, Swift Concurrency migration and pitfalls, performance attribution (the Instruments templates), quantified governance of launch time and app size, modularization and dependency management, App Store review and staged rollout practice, and the boundary between Objective-C and Swift in mixed projects. iOS interviews at top companies often have a "hand-written algorithm + language and runtime + project deep dive" structure; this pack covers the iOS-specific parts of language, runtime, and project deep dive.

How to ask like an interviewer in this field:
- Memory and the runtime are the hard bar in iOS interviews: start from real symptoms like "deinit is never called" or "intermittent crash" and have the candidate draw the ownership chain or explain dispatch; flag candidates who can recite the ARC definition but cannot draw the ownership chain.
- SwiftUI and Swift Concurrency are the two areas that best separate depth right now: start from "state got reset", "the actor went negative", or "the request is still running after the page closed"; do not ask list questions like "what property wrappers does SwiftUI have".
- Performance questions must land on Instruments templates and production data: real experience with Time Profiler, Core Animation, App Launch, Allocations, and MetricKit is a hard bar for experienced hires.
- Do not test version trivia: do not ask "what APIs were added in iOS 18"; test how they troubleshoot behavior changes and approach compatibility. Platform-agnostic questions on launch, app size, staged rollout, and cross-platform go to the parent pack mobile.

## Probing projects and internships

Where to start and what to press on when the resume contains the following kinds of experience. Keep going until the candidate can describe the mechanism, where the numbers came from, and one real failure or trade-off; if they can only name the framework and the conclusion and cannot describe their own part, record it as a red flag. For the general follow-up method see project-deep-dive.

- Resume mentions a SwiftUI project / migration → press on which screens use it, the minimum supported version, how state management is organized, the boundary with UIKit in mixed code, and the hardest view-update problem they hit
- Resume mentions a Swift Concurrency migration → press on what they migrated from, how Sendable checking was handled, whether they got bitten by actor reentrancy, and how cancellation is handled when bridging old APIs
- Resume says "launch time optimized X%" → press on the split between pre-main and post-main, the attribution tool, whether they merged dynamic libraries and did binary reordering, and how they verified it
- Resume says "app size reduced X MB" → press on Link Map attribution, the biggest few sources, handling of resources and Swift specialization, and whether there is a CI gate
- Resume says "crash rate / jank rate dropped" → press on the top root causes, how OOM and watchdog kills are identified, MetricKit or a self-built solution, whether crash protection is used and its side effects
- Resume mentions componentization / modularization / build speedup → press on the basis for splitting frameworks, static or dynamic, build time numbers before and after, and dependency manager migration
- Resume mentions a legacy Objective-C project / mixed stack → press on the migration strategy, the boundary of the bridging layer, and which Runtime hacks exist and their risks
- Resume mentions App Store rejection / staged rollout → press on the rejection reasons and fixes, how TestFlight and phased release are used, and the compliance boundary of dynamic delivery

## Common failures and red flags

- ARC, retain cycles, and memory semantics: can only say "add weak self in the closure" but cannot say who holds whom in the cycle; does not know the Timer is held by the RunLoop; thinks Swift does not need autoreleasepool; puts weak on every closure, including non-escaping ones
- Swift language features and performance: can only recite "struct on the stack, class on the heap"; does not know about existential container overhead; cannot explain how final affects dispatch
- UIKit view system and layout: does not know the relationship between layoutSubviews and setNeedsLayout; does not implement prepareForReuse for reused cells; attributes all jank to "images too large"
- SwiftUI state and view updates: cannot tell @StateObject from @ObservedObject; thinks a body recomputation means re-rendering the whole view tree; does not know the concept of view identity
- GCD, locks, and thread safety: believes async always spawns a new thread; does not know QoS and priority inversion; treats semaphore as a universal sync tool and waits on the main thread
- Swift Concurrency and actors: thinks an actor is just automatic locking; does not know await is a potential suspension point and actor state can change during suspension; calls semaphore.wait or sleep inside an async function; Tasks without cancellation handling
- Combine and reactive data flow: does not know Cancellable must be retained; thinks @Published emits in didSet; handles errors with catch and then ignores that the stream has terminated
- Runtime, method dispatch, and Objective-C interop: can recite the three stages of message forwarding but cannot name a practical use; does not know Swift methods do not go through message sending by default; when swizzling, does not handle the case where the method is implemented only in the superclass
- Performance analysis and jank monitoring: only knows Time Profiler, not the Core Animation template; does not know a RunLoop observer can be used for jank monitoring; has no jank data in production
- Crashes, symbolication, and production stability: does not know how dSYM and UUID correspond; thinks OOM can be caught with a stack trace like a normal crash; uses a "crash protection" library to swallow all exceptions and is proud of it
- App lifecycle, background, and system interaction: believes the background can run tasks freely; does not know beginBackgroundTask has a timeout; has no concept of the scheduling uncertainty of BGTaskScheduler
- Launch optimization and app size: does not know the pre-main phase exists; launch optimization means only "move initialization later"; has no Link Map analysis experience
- Dependency management, engineering, and release: cannot tell how static vs dynamic libraries affect launch and app size; has never looked at a build timeline; mixes SPM and CocoaPods without knowing about duplicate symbols

## Frequently tested topics

Only names, ladders, and signs of a solid answer are listed, as a reference for "how deep counts as solid". Which topics to ask and how many is decided by this JD and this resume; it is not a quota.

### ARC, retain cycles, and memory semantics
- Ladder: what ARC is, the difference between strong/weak/unowned → how reference counting is implemented in Swift (side table, weak reference zeroing), the semantics of closure capture lists, when autoreleasepool is still needed in Swift → when deinit is not called after a page is popped, how to find the retain cycle with Memory Graph Debugger or Instruments Leaks, the leak shapes of Timer, NotificationCenter closures, and strongly held delegates → the performance and safety trade-off between weak and unowned, when unowned is worth using, how to roll out the convention for capturing self in closures across a team
- Signs of a solid answer: can draw the complete ownership chain (RunLoop → Timer → closure → self); knows invalidate is required to break it; understands that accessing unowned after the object is freed crashes; has real experience locating leaks with Memory Graph or Leaks; knows a loop that creates many temporary objects needs autoreleasepool

### Swift language features and performance
- Ladder: value types vs reference types, choosing between struct and class → how copy-on-write (COW) is implemented and triggered, dispatch for protocols and generics (existential containers, witness tables, specialization), dispatch kinds (static, table, message) → an array repeatedly mutated in a loop causing many copies, an array of protocol types performing far worse than generics: how to attribute it → the trade-off between the safety of value semantics and copy cost, when to use final/private to help compiler optimization, the relationship between generic specialization and binary size
- Signs of a solid answer: can explain the isKnownUniquelyReferenced check behind COW; understands the indirection and inline buffer of existential containers; knows how @inlinable and module boundaries limit optimization; is aware of how Swift 6 strict concurrency checking affects value types

### UIKit view system and layout
- Ladder: view hierarchy, frame vs bounds, basic AutoLayout use → constraint solving in the layout engine and when layoutSubviews runs, reuse and self-sizing in UITableView/UICollectionView, Compositional Layout and Diffable Data Source → how to locate dropped frames in list scrolling with Instruments' Core Animation or Time Profiler (too many constraints, offscreen rendering, main-thread decoding, repeated self-sizing computation), how to fix scrambled content caused by cell reuse → trade-offs between hand-written frames and AutoLayout, the benefit and maintenance cost of precomputing heights, choosing between Diffable and manual reload
- Signs of a solid answer: can read the offscreen rendering and color blending flags in the Core Animation template; has experience precomputing layouts or caching heights; knows Diffable's hash and identity requirements; understands the relationship between estimated and real height in self-sizing

### SwiftUI state and view updates
- Ladder: the fundamental difference between SwiftUI and UIKit, what @State is → the storage location and lifecycle of each property wrapper (@State/@StateObject held by SwiftUI, @ObservedObject held externally), view identity and body recomputation, what the Observation framework changed → how to locate views unexpectedly rebuilt when the parent refreshes and losing state, objects repeatedly created by passing @ObservedObject, all rows recomputing during list scroll (Self._printChanges, the Instruments SwiftUI template) → the boundary of mixing SwiftUI and UIKit (coordinates and lifecycle of UIViewRepresentable), which screens are not suited to SwiftUI, how the minimum OS version limits API availability
- Signs of a solid answer: can say that SwiftUI views are values and state lives in the framework's storage; knows how structural identity and explicit id affect animation and state; has experience locating excess updates with _printChanges or Instruments; is aware of @Observable's per-property dependency tracking

### GCD, locks, and thread safety
- Ladder: serial and concurrent queues, sync vs async, the main queue → how deadlocks form (sync on the main queue), DispatchGroup/Semaphore/barrier, QoS and priority inversion, performance and semantics of common locks (os_unfair_lock, NSLock, read-write locks) → intermittent crashes from multithreaded access to arrays or dictionaries, how to locate data corruption from data races with Thread Sanitizer, how to handle thread explosion from many tasks on a concurrent queue → global concurrent queue vs self-built queues, lock granularity and performance, when to move to actors
- Signs of a solid answer: understands the relationship between queues and threads (a queue is not a thread); knows barrier works only on self-built concurrent queues; has real use of TSan; can state the cause of thread explosion (many blocking tasks on a concurrent queue)

### Swift Concurrency and actors
- Ladder: what async/await solves compared with closure callbacks, what a Task is → structured concurrency (child tasks and cancellation propagation), actor isolation and reentrancy, MainActor, Sendable and data race checking, the cooperative thread pool → how to investigate a request still running after the page closed when it was started with a Task, actor state changed by someone else after an await inside an actor method (reentrancy), synchronous blocking code inside async starving the thread pool → strategy for migrating from GCD/closures to Swift Concurrency, the migration cost of Swift 6 strict concurrency checking, when to keep GCD
- Signs of a solid answer: can state actor reentrancy semantics and the defense (check state before suspending or use a state machine); understands that structured-concurrency cancellation is cooperative (Task.checkCancellation); knows the cooperative thread pool is about the core count and blocking starves it; has experience bridging delegate/closure APIs to async (withCheckedContinuation) and handling cancellation

### Combine and reactive data flow
- Ladder: the basic relationship of Publisher/Subscriber/Operator → backpressure and demand, kinds of Subject, subscription lifecycle and AnyCancellable, schedulers and thread switching → subscriptions still calling back after a page pop, @Published reading the old value at willSet timing, an error in a Combine chain terminating the whole stream: how to investigate → the division of labor between Combine and async/await, which scenarios still justify Combine (merging multiple sources, debounce), migration cost
- Signs of a solid answer: knows how flatMap and switchToLatest differ regarding races; uses replaceError or restarts the stream after catch; understands the difference between receive(on:) and subscribe(on:); has a judgment on choosing between Combine and AsyncSequence

### Runtime, method dispatch, and Objective-C interop
- Ladder: Objective-C message sending vs Swift dispatch → objc_msgSend, the method cache, the three stages of message forwarding, how KVO's isa-swizzling works, what @objc dynamic does → how to investigate intermittent crashes or odd behavior from Method Swizzling (repeated exchanges, category conflicts, compatibility when hooking system methods), why a Swift class's method cannot be found when called from OC → the benefit and maintenance risk of using swizzling for tracking and silent fixes, the trade-off between bridging headers and modularization in mixed projects, strategy for migrating old OC code to Swift
- Signs of a solid answer: understands the combination of class_addMethod and method_exchangeImplementations; knows how KVO derives a subclass and the limits of Swift KVO; has a judgment on alternatives to swizzling (subclassing, protocol extensions, AOP libraries)

### Performance analysis and jank monitoring
- Ladder: what the common Instruments templates show (Time Profiler, Allocations, Leaks, Core Animation, Hangs) → main-thread RunLoop observation points and the jank detection principle (RunLoop state timeout plus stack capture), offscreen rendering and layer blending, MetricKit's capabilities → jank rate is high in production but cannot be reproduced locally: how to attribute stacks using MetricKit and self-built jank monitoring, common root causes of App Hangs (main-thread IO, locks, synchronous networking, heavy AutoLayout) → the sampling overhead and stack aggregation strategy of jank monitoring, which janks give the highest ROI to fix
- Signs of a solid answer: can explain RunLoop-based jank detection and how false positives are handled; knows MetricKit's collection delay and sampling limits; has attributed causes from Time Profiler flame graphs; understands how main-thread IO and lock waits differ in stack appearance

### Crashes, symbolication, and production stability
- Ladder: crash types (Objective-C exceptions, signals, watchdog, OOM) and how they are collected → the symbolication flow (dSYM, UUID matching), the relationship between Mach exceptions and Unix signals, how crash-collection SDKs work and conflicts between multiple SDKs → symbolication failure, stacks inside system libraries, OOM with no stack: how to attribute (memory watermark collection, foreground OOM determination), how to investigate a watchdog timeout (0x8badf00d) during launch → the tug of war between crash rate and business iteration, feasibility and review risk of hot fixes on iOS, side effects of crash protection (NSException fallback, array out-of-bounds interception)
- Signs of a solid answer: can state how FOOM is determined (by elimination); understands the ordering in the signal handler chain; has experience handling watchdog and launch timeouts; shows restraint about where crash protection applies

### App lifecycle, background, and system interaction
- Ladder: app states (active/inactive/background/suspended) and AppDelegate/SceneDelegate callbacks → background execution time, the Background Tasks framework, push and silent push, state preservation and restoration, multiple Scenes → a white screen or corrupted data after the user backgrounds and returns, background tasks terminated by the system, pushes not arriving: how to investigate → applying for background capabilities and review, the boundary of keep-alive and user trust, the cost of adopting Scene support
- Signs of a solid answer: distinguishes short background tasks from BGProcessingTask; knows URLSession background sessions can resume across processes; understands the difference between suspended and killed; is aware of SceneDelegate and multi-window

### Launch optimization and app size
- Ladder: cold-launch phases (pre-main and after main), what happens in pre-main (dyld loading, rebase/bind, +load, static initializers) → dyld 3/4 closure caching, the effect of the number of dynamic libraries, Order File and binary reordering (page faults), Link Map analysis of app size → how to attribute a 300ms launch regression using DYLD_PRINT_STATISTICS or Instruments App Launch, how to attribute a 20MB size increase to modules and SDKs with Link Map → the benefit and engineering cost of merging dynamic libraries into static ones, diminishing returns of binary reordering, the operational cost of On-Demand Resources
- Signs of a solid answer: can explain the dyld loading flow and where time goes in each phase; knows the cost of +load and static initializers; has experience analyzing app size with Link Map or third-party tools; is aware of how App Thinning, resource compression, and Swift generic specialization affect size

### Dependency management, engineering, and release
- Ladder: differences between CocoaPods and SPM, Xcode projects and workspaces → static vs dynamic libraries, modularization (framework splitting, inter-module interfaces), attributing Xcode build time (-Xfrontend -warn-long-function-bodies, build timeline), xcconfig and multiple environments → how to attribute a 20-minute build (Swift type inference, module granularity, dependency graph), how to resolve SPM dependency version conflicts → monorepo with multiple frameworks vs multiple repos, build caching solutions on CI, common causes of App Store rejection and staged rollout strategy (TestFlight, phased release)
- Signs of a solid answer: can read the build timeline and long-function-body warnings; knows the relationship between whole-module and incremental compilation in Swift modules; has practice with xcconfig and CI caching; is aware of App Store review rules (privacy manifests, third-party SDK signing, dynamic delivery limits)
